# Следующие задачи

Спецификация самодостаточна: её хватит, чтобы продолжить работу, не читая историю обсуждения.

## 1. История упражнения и настоящие личные рекорды

Сейчас про упражнение видно только `lastResult` — результат прошлой тренировки. Все подходы лежат в `exercise_sets`, но посмотреть динамику нельзя.

### Backend

Ключ истории — `exercise_templates.exercise_id` (id записи каталога), а **не** `exercise_templates.id`. Строка шаблона живёт в пределах одной тренировки, а каталожный id общий: одно и то же упражнение в разных тренировках должно давать одну историю. У строк, оставшихся от старой схемы, `exercise_id` пустой — для них резервный ключ `exercise_templates.name`.

Запрос: подходы из `workout_sessions` со `status = completed` и `is_completed = true`, принадлежащие владельцу, сгруппированные по сессиям и упорядоченные по `completed_at`.

Новая функция в `backend/app/services.py`:

```python
async def exercise_history(db, owner, exercise_id: int, limit: int = 12) -> dict
```

Возвращает:

- `records` — `max_weight_kg`, `max_reps`, `max_session_volume_kg`, у каждого дата достижения;
- `sessions` — до `limit` последних: дата, лучший вес, суммарный объём, список подходов.

Эндпоинт: `GET /api/v1/exercises/{exercise_id}/history`, доступ `require_owner`.

### Честный бейдж рекорда

Бейдж «+1 PR» с экрана завершения снят: он был захардкожен и поздравлял с рекордом после каждой тренировки. Вернуть его следует только вместе с расчётом.

Добавить в `complete_workout` определение рекордов текущей сессии: для каждого упражнения сравнить лучший вес и объём этой сессии со всеми предыдущими завершёнными сессиями владельца (**исключая текущую**). Строго больше — рекорд. Результат положить в ответ ключом `records`, фронт покажет его на экране завершения.

### Frontend

`_workout_template_payload` пока не отдаёт каталожный id — добавить `exercise_id` в `_exercise_payload`, в `mapExercise` прочитать как `catalogId`, в типе `Exercise` объявить `catalogId: number | null`.

Показывать историю в уже существующей модалке `ExerciseInfoModal` (`frontend/src/screens/WorkoutScreen.tsx`) — новых экранов и пунктов навигации не добавлять.

График рисовать вручную через SVG, **не** подключая recharts: библиотека сейчас лежит в отдельном чанке `ProgressScreen` (~390 КБ), импорт в `WorkoutScreen` утянет её в основной бандл.

В демо-режиме (`USE_MOCKS`) вернуть правдоподобный ряд, иначе на демо-сборке раздел будет пустым.

## 2. Оценка тренировки на финише

`api.completeWorkout` шлёт захардкоженное `{ perceived_exertion: 8 }`, поле `notes` не заполняется никогда. Оба поля в модели `WorkoutSession` есть.

Добавить в диалог подтверждения «Завершить тренировку?» ряд оценки 1–10 и необязательную заметку, значения передавать в `completeWorkout(sessionId, { perceivedExertion, notes })`.

Побочный выигрыш: и то и другое входит в контекст AI-анализа недели, который сейчас получает по этим полям пустоту.

## Чего делать не стоит

Суперсеты, разминочные подходы, база продуктов, соцфункции, интеграция с часами. Каждое — отдельный экран или заметное усложнение существующих; приложение задумано компактным.

## Как проверять

Панель предпросмотра в среде разработки не отрисовывает кадры (`visibilityState: hidden`, ноль вызовов `requestAnimationFrame`), поэтому интерфейс на `framer-motion` в ней не проверить: переходы между экранами не завершаются, клики по `motion.button` не доходят. Проверять логику сценарными скриптами против `sqlite+aiosqlite:///:memory:`, а интерфейс — на устройстве через демо-сборку.

Внешние ключи в таких скриптах включать явно, иначе поведение разойдётся с боевым:

```python
@event.listens_for(engine.sync_engine, "connect")
def fk_on(dbapi_conn, _):
    dbapi_conn.cursor().execute("PRAGMA foreign_keys=ON")
```

Обязательные прогоны перед коммитом:

```bash
python -m pytest -q
cd frontend && pnpm typecheck
```
